# ColmCast Chatbot v2: Architectural Evaluation and Roadmap
## Current Architecture (Slack-Based v1) – Strengths and Decisions

The ColmCast v1 system is implemented as a monolithic Python chatbot integrated with Slack. It uses the Slack Bolt framework to handle message events and a GPT-4 API for generating responses. 

### Key technical decisions in this design include:
- **LLM Integration with RAG**: The bot employs retrieval-augmented generation – it ingests D&D rulebooks and source material into a FAISS vector index (via LlamaIndex) to provide contextually accurate answers. This allows the chatbot to answer rules or lore questions with precise references from 5e source texts, rather than relying on the model’s memory alone.
- **Persona and Prompt Engineering**: A rich system prompt defines the bot’s persona as “CC” (Colm Cassidy’s digital avatar), with a darkly witty tone and knowledge of D&D mechanics. The prompt explicitly instructs CC to use player profile details and the D&D rule context when responding, ensuring the chatbot remains in-character and mechanically accurate.
- **Player Profiles and Lore Context**: The bot loads custom JSON files for player profiles and lore data at startup. This enables CC to tailor responses to each player’s character backstory and the campaign lore, enhancing immersion. The persona is context-aware and draws from these profiles during conversations (e.g. referencing a character’s traits or past).
- **Conversation History & Logging:** To maintain continuity in DM (direct message) chats, the script stores recent dialogue history per user in JSON files (up to 10 recent turns) and logs all DM conversations to a file. This provides memory of context within a session and also creates an audit log for the Dungeon Master to review later. The use of file-based logs is simple but effective for the one-shot scenario.
- **D&D Mechanics Library**: The codebase includes the dnd-character Python library (originally by tassaron) to handle D&D 5e mechanics and character data. This library programmatically generates characters, classes, items, monsters, etc., using SRD rules fetched from an API and cached locally. By bundling this library, the chatbot can eventually create and manipulate actual character stat blocks rather than relying purely on GPT’s imagination. This decision shows foresight in ensuring mechanical consistency for things like ability scores, inventory, HP leveling, and so on.
- **OpenAI and Tools Setup**: The environment is configured with OpenAI GPT-4 via API (with keys from .env), and includes modern NLP tooling (LangChain, LlamaIndex, etc.) as listed in the environment.yml dependencies. The use of a FAISS index with LlamaIndex is a strength: it means the bot can semantically search the loaded rulebooks (Player’s Handbook, DM Guide, UA articles, etc.) for relevant passages. This gives high accuracy when players ask complex rules questions (e.g. “How does concentration work for spells?”) – the bot will retrieve the rules text and include it in the GPT prompt for a correct answer.

Overall, ColmCast v1’s architecture successfully combines a rule-based engine with a generative model. The strengths lie in its knowledge depth and character roleplay:

- **Deep D&D Knowledge**: By embedding the entire 5e SRD (and beyond) into a vector store, the bot can pull exact rules wording or descriptions on demand. This mitigates GPT’s tendency to hallucinate game rules.
- **Immersive Persona**: The carefully crafted system persona for CC yields flavorful, in-character responses that enrich the game’s narrative. The bot responds as a “cryptic, clever, sinister” NPC, giving players the feeling they are texting with the villain himself.
- **Integration of Game State**: The inclusion of dnd-character means the bot isn’t just a freeform AI – it can eventually output real stat blocks or resolve dice mechanics using the same formulas as the tabletop rules. For example, the library can automatically manage leveling (experience to level-ups) or generate a character’s starting equipment correctly, ensuring any game outputs are rules-compliant.

These technical decisions provide a solid foundation: ColmCast v1 is context-rich, thematically consistent, and rules-accurate. It effectively turned a Slack channel into an interactive D&D NPC with both storytelling and rules adjudication capabilities.

### Limitations of v1 (Slack Script) and Need for Change
Despite its strengths, the Slack-based monolith has notable gaps that drive the transition to a new architecture:

- **Slack as a Platform**: The original deployment via Slack made sense for quick prototyping, but it limits player accessibility. Slack requires invitations to a workspace, whereas the D&D group can more easily gather on Discord. Additionally, Slack’s API and Socket Mode approach require a persistent connection and are geared toward enterprise chat; it’s not as natural a fit for a D&D bot as Discord’s gaming-focused environment. In short, Discord is the preferred UX for players. By moving to Discord, ColmCast can reside in a familiar D&D milieu – with support for voice channels, rich embeds for character sheets, and broader community access (no corporate workspace needed).
- **Monolithic and Tightly Coupled**: In v1, all logic – from message handling to AI prompting to dice rolling – lives in one Python process. This makes it harder to extend or modify features on the fly. For example, adding a new command (say, !inventory to list a character’s items) would require editing the Python code, redeploying the bot, and possibly disrupting the running session. There’s little modularity. This tight coupling also makes maintenance riskier: a bug in one part (e.g., the RAG retrieval) could crash the entire bot. A more modular design (with separate components or workflows) would isolate such issues.
- **Scalability and Extensibility**: The current design is not easily scalable beyond the one-shot scenario. If multiple campaigns or channels wanted to use CC simultaneously, the single Slack app instance would need significant refactoring. There’s also no straightforward way to integrate new capabilities or external services (e.g., scheduling a future event or integrating with a database) without writing additional Python code. The n8n automation framework is appealing here because it excels at orchestrating multiple services and logic branches in a visual workflow. It would allow scaling out new features by connecting “nodes” rather than rewriting code for each integration.
- **Dynamic Updates**: The team desires dynamic feature updates via n8n, meaning the ability to tweak or add bot behavior during the campaign runtime. With the Slack bot, any change required a code push. In a fast-moving campaign, being able to adjust the bot’s behavior on the fly (e.g., enable a new puzzle interaction, or adjust how a rule is handled) is valuable. N8n, with its live workflow editing, offers this flexibility – you can modify a workflow or add a new one, and it takes effect immediately, without restarting the whole system.
- **Maintainability**: As the project grows (more sourcebooks, more custom rules), a single script becomes unwieldy. Already, the repository shows complex setup steps (building indexes, handling environment variables, etc.), which can be error-prone on each run. Containerizing the components will improve reliability by encapsulating dependencies. The development workflow can also improve – for instance, using a dev container (as indicated by the .devcontainer/ and recent commit) and Docker ensures consistency between dev and prod environments. Without containerization, installing the correct versions of Slack SDK, LlamaIndex, PyTorch/FAISS, etc., is a hurdle for any new maintainer. Packaging these in Docker images will greatly simplify setup and updates.

In summary, the Slack-based v1 is a strong prototype but not the ideal end-state. It demonstrated the concept – a GPT-powered D&D NPC – but now the project needs to:

- Migrate to Discord for better player engagement and interactive features.
- Refactor into a modular architecture (with n8n and microservices) for agility and easier maintenance.
- Enhance support for custom content (beyond SRD) in a sustainable way.

These changes will address the pain points of v1 while opening the door for a more powerful and extensible ColmCast v2.

## New Modular Architecture (n8n + Discord) – Design Overview
ColmCast v2 will evolve into a containerized, modular system orchestrated by n8n, with Discord as the primary user interface. The high-level architecture consists of:

- **n8n Automation Workflows**: At the core, an n8n instance will host workflows that define the bot’s logic as interconnected nodes. Each discrete feature or interaction can be a separate workflow or sub-workflow. For example, there will be a workflow for the main conversational loop (handling incoming player messages to CC) and separate workflows for game commands like rolling dice or managing character data.
- **Discord Bot Integration**: Instead of Slack events, the system will rely on Discord. We will create a Discord Bot user for ColmCast and connect it to n8n. The integration can use Discord’s slash commands and webhooks to trigger n8n workflows. In practice, this means defining slash commands like /CC (for in-character chat) or specific commands like /roll or /statcheck. When a player invokes these in Discord, the bot (via n8n) will receive the command payload and start the corresponding workflow. This approach achieves parity with Slack’s UX: players can DM the bot or use commands in a channel, and the bot will respond in Discord just as it did in Slack. Thanks to Discord’s support for rich interactions, we can even add buttons or menus later (via Discord component interactions) for things like choosing from a list of characters – n8n has community nodes to handle such interactive messages.
- **Microservice for Game Logic (Python)**: The D&D-specific computations and data management will be handled by a dedicated Python service container. This service will encapsulate the dnd-character library and any custom game logic. It exposes a simple REST API that n8n can call (using HTTP Request nodes). For instance, n8n might call POST /character/generate with parameters to create a new level 10 character, or GET /character/{name} to fetch a stored character’s stats. The service can also provide endpoints for dice rolls or rule lookups (if we choose to implement some rule logic in Python). By decoupling this from the chatbot workflow, we achieve modularity:

	- The Python service can be updated or extended independently (e.g., update the dnd-character version or add new endpoints for homebrew rules) without altering the n8n workflows.
	- n8n acts as the “conductor”, deciding when to call the Python service and handling the flow of data between Discord, the AI model, and the game logic service.
	
- **OpenAI API (GPT-4) via n8n**: The conversational AI calls to GPT-4 will now be performed within the n8n workflows. N8n provides an OpenAI integration node (or we can use a generic HTTP node to call OpenAI’s API). The workflow will construct the prompt – including the system persona and any retrieved context – then invoke GPT-4, and finally post-process and send the response back to Discord. This means we no longer run an OpenAI client inside a long-lived Python process; instead each query is a stateless API call triggered by the workflow. In effect, n8n orchestrates the RAG loop: Trigger → retrieve context → compose prompt → call GPT → respond. The logic from the Slack script can be reimplemented in this node-based fashion. For example, the step that queries the FAISS index for relevant rule text can be an “Execute Command” node running a small Python snippet or an HTTP call to a “search service” (more on this below).
- **Vector Index & Knowledge Base**: We will reuse the FAISS vector index built from D&D sourcebooks (the content in 5e_SourceBooks/ like the Player’s Handbook, Monster Manual, UA PDFs, etc.). In v2, we have two options to integrate this:
- **Embed in Python Service**: Load the FAISS index inside the Python game logic service on startup. We can utilize the same LlamaIndex code (rag_retriever.py) to load the persisted index and handle queries. Then expose an endpoint like POST /query_rules that accepts a natural language question and returns the top relevant text snippets from the rulebooks. N8n can call this endpoint when it needs context for a rules question.
- **Dedicated Vector DB**: Alternatively, spin up a dedicated vector database (like ChromaDB or Qdrant) and populate it with the embeddings. This would be a separate container accessible to n8n via an API or plugin. However, given we already have a working FAISS index and LlamaIndex integration, it’s simplest to keep using that inside our Python service. The v1 code will largely carry over – e.g., the query_index() function that returns context given a query can be invoked via an API call.
- **State Management**: N8n can maintain state or data between steps in various ways. For short-term context (like conversation history), the workflow can fetch the last N messages from a database or cache. For long-term data (like character sheets, or which character a player has chosen), we will integrate a lightweight database or use n8n’s built-in data storage. One approach is to use n8n’s Credential Vault or Data Store nodes to save key–value pairs (for example, map a user’s Discord ID to their chosen character’s name/stats). Another approach is to have the Python service or a small database container (Postgres or even SQLite) store persistent game data, which n8n can query. Since the question focus is architecture, we note that state can be externalized – the Slack file-based logs will likely be replaced by either database records or just reliance on Discord’s history plus the vector index for long text search.

In this architecture, n8n is the hub connecting Discord, the AI model, and the game logic service:

- Workflows can be versioned and managed visually, making it easier to reason about the bot’s behavior than diving into a single large Python file.
- Features can be enabled/disabled modularly. For instance, during playtesting if the DM finds the automated dice rolls problematic, that particular workflow can be turned off without affecting the core chatbot conversation.
- It also becomes easier to integrate other services. If we want to, say, send a summary of the session to an email or log something in a Google Sheet, n8n has nodes for those. This extensibility aligns with the project’s needs to adapt to dynamic storytelling (perhaps integrating images, maps, or other tools later).
- Finally, containerization via Docker Compose or Kubernetes will tie everything together. The user’s GitHub profile indicates a fork of n8n-io/n8n-hosting, which provides examples for self-hosting n8n in Docker. We will leverage those patterns:

	- One container for n8n (workflow engine, includes web UI to edit flows).
	- One container for ColmCast Game Logic API (Python + dnd-character + FAISS index).
	- Possibly an additional container for a database (if needed for persistence or n8n’s own data). n8n can use an SQLite by default, but production use often involves a PostgreSQL container for reliability.

This modular setup improves maintainability and deployment:

- Each container can be built and tested in isolation. For example, the Python service can have its own CI to run unit tests on any custom dnd-character enhancements.
- Using environment variables and .env files (similar to v1) will continue – e.g., Discord bot token, OpenAI API key, etc., will be injected into n8n’s config or the Python service config securely, not hard-coded.
- The Discord bot just needs to be invited to the server and given the appropriate scopes (applications.commands, bot permissions). It will essentially act as a relay between Discord and our n8n instance.

In essence, ColmCast v2’s architecture is centered on loose coupling: Discord triggers -> n8n workflow -> specialized service calls. This will greatly facilitate “dynamic feature updates,” as adding a new feature might be as simple as drawing a new branch in the n8n workflow canvas or writing a small new endpoint, without touching the core logic of the other parts.

### Discord UX Parity and Enhancements
Achieving Discord UX parity with the previous Slack experience is a priority. In Slack v1, players would DM “CC” or mention the bot in a channel, and the bot replied in-character. We can mirror and even enhance this in Discord:
- **Direct Messages**: We can allow players to privately message the ColmCast bot on Discord. Discord bots by default cannot start a DM with a user, but they can reply if a user DMs them first. Using n8n’s Discord triggers (via a community node or a webhook), we will catch DMs to the bot and funnel them into the main conversation workflow. This means a player can have a private, immersive dialogue with “CC” just like before. For the player, the experience is identical – they message the bot, and it replies with CC’s persona.
- **Public Channel Interactions**: In Slack, CC might have been confined to DMs. On Discord, we have the opportunity to also use it in a shared channel (for example, a “#train-chat” channel representing the in-game communications). Using slash commands is a safe way to do this in Discord without the bot responding to every message (which could become spammy). For instance, a player could type /cc ask "Where are we heading?" in the channel, and the bot could respond publicly in-character so all players see it. We can make the slash command such that if used in a server channel, it sends the reply either publicly or as an ephemeral message visible only to the user (ephemeral responses could be useful to avoid spoilers or clutter). The n8n workflow can examine the context of the command and choose how to respond (Discord’s API supports ephemeral responses to slash commands).
- **Slash Commands for Game Mechanics**: We will define additional slash commands for common game tasks. Some examples:

	- /roll `1d20+5` – The bot parses the dice expression and returns the result. (This could use a simple dice-rolling code in the Python service or even a lightweight JS library in an n8n Function node.)
	- /stats – The bot PMs the user their current character’s stat block or posts a nicely formatted embed of their character sheet.
	- /equip `item` – The bot updates the character’s inventory (via the Python service’s Item logic) and confirms the action, possibly also recalculating armor class or other effects.
	- /abilitycheck `insight` – Bot rolls an Insight check for the character, applying their modifiers from the character data.
	- /help – Lists available commands and a brief how-to, easing onboarding for players not used to slash commands.

Using Discord’s slash commands has two benefits: discoverability (players can see available commands by typing / and finding CC’s commands) and structured input (we can define expected parameters, making it easier to parse). The n8n workflows will correspond one-to-one with these commands, which keeps the logic organized. 

We will need to implement a small portion of Discord bot setup:
Registering the commands with the Discord API (either via a bot command or through a configuration in n8n if supported). This typically involves providing a JSON schema for each slash command (name, description, parameters) to Discord. Once registered, the commands will appear for users. Permissions: Ensure the bot has permission to read messages and send messages in the intended channels. For private interactions (DMs or ephemeral), no special channel permission is needed.

The Discord UX also gives us more possibilities:
We can use embeds to present richer information. For instance, when showing a character sheet, instead of a plain text block, the bot could send a formatted embed with fields for each ability score, HP, etc., or even attach an image of a character (if art is available). This was harder in Slack (Slack has attachments but not as rich as Discord’s).
We can utilize reactions or buttons for simple choices. Imagine a scenario where CC poses a question to the group (“Do you pull the lever?”) – we could have the bot add reaction emojis for Yes/No that players can click, or use Discord’s Message Components (buttons) where each button click triggers an n8n workflow path. A community-contributed Discord Trigger node supports interactive components, which could be a future extension for interactive puzzles or combat choices.
Parity with Slack is essentially achieved through DMs and slash commands, but Discord will ultimately offer a superior UX:
No need for “mention removal” hacks (in Slack code we saw they stripped out the bot mention from text) – Discord slash commands deliver clean input strings to the bot.
Easier out-of-character communication: If needed, we could have a separate command or channel for OOC queries (like rules clarifications) that CC could answer distinctly.
In implementing the Discord layer, we will follow best practices from the n8n community:
Use a Webhook trigger for slash commands: Discord can be set to send an HTTPS POST to a specific URL when a slash command is invoked (this is how interactions work under the hood). n8n’s Webhook node can catch this. Alternatively, use the Discord Trigger community node which abstracts some of this. Either way, the workflow starts when a Discord interaction comes in.
A Discord Send Message node (or simply an HTTP response to the interaction) will be used to send replies. If using slash commands, we must acknowledge the command within 3 seconds. n8n can handle this by sending an immediate defferal (a tiny ACK response) and then a follow-up message when the GPT response is ready. This ensures we don’t hit Discord’s 3s timeout for interactions even if GPT-4 takes 5-6 seconds to respond. The user will see a “CC is thinking..." indicator until the answer appears.
By carefully designing these interactions, players should experience a seamless conversation with ColmCast on Discord, just as they did on Slack, with even more polish. The narrative immersion remains top priority – technology should not get in the way. With the above setup, players can freely chat, ask questions, and issue commands, and ColmCast will respond promptly in character, now on a platform they are comfortable with.

### Extensible Game Logic with dnd-character Library
A major goal for v2 is to have extensible game mechanics logic, leveraging an updated dnd-character library to handle character creation and rule computations. This means moving beyond the base SRD content and supporting custom or homebrew elements (e.g. new classes, items) relevant to our campaign. Here’s the plan for implementing this:
- Update dnd-character to Latest & Customize: First, ensure we have the latest version of the dnd-character library (the original repository by tassaron was archived in June 2025) and apply any custom patches. The library in v1 was designed around 5e SRD only – it fetches data from the open 5e API and caches it. We will modify this:
- Point to Local Data: Instead of the live API (dnd5eapi.co), we can configure the library to use a local dataset. The repository already includes a fork of the 5e-database (5e-bits), which contains JSON data for all official 5e content (spells, classes, etc.). We can host this data via a lightweight local API or file system. By setting the SRD_API environment variable to our local endpoint, the library’s SRD calls will pull from our comprehensive dataset instead of the limited SRD API. This instantly expands the library’s knowledge to things like Artificer, Blood Hunter, Eberron races, spells from Tasha’s Cauldron, etc., assuming those are present in the 5e-bits dataset.
- Pre-Cache Homebrew Entries: For truly custom content not in any DB (e.g. a “School of Geometry” wizard subclass unique to our game, or the Mr. Comcast (ColmCast) stat block), we will manually add JSON entries to the library’s json_cache. The library is designed to load any JSON files in that cache at startup. We can drop in files like classes_artificer.json or subclasses_school_of_geometry.json with the exact format the library expects. When the library initializes, it will incorporate these into its internal data structures as if they were fetched from the API. This approach lets us “inject” homebrew content seamlessly. For example, adding Artificer this way means dnd_character.classes.Artificer could become available just like the standard classes, and Character(classs=CLASSES['artificer']) would work in code.
- Verify Class Modeling: Some new classes might need code support. The core 12 classes are implemented as Python classes in dnd_character.classes (for features like spell slots, etc.). For Artificer or Blood Hunter, we might write analogous classes by inheriting from the base Character or similar class. If we don’t implement a full class class, we can still use the generic Character object and manually adjust its attributes to simulate that class. However, given the commitment to accuracy, writing a minimal Artificer class (perhaps borrowing logic from Wizard for spellcasting and from Fighter for extra infusions) would be ideal. We will document any such additions in the code.
- Custom Equipment and Items: Homebrew items (e.g., a magical “Arcane Locomotive Key”) can be added by extending the item JSON data. The library’s Item(name) lookup will search cached item data. We can append new items in equipment.json in the cache or create separate files. The same cached loading mechanism will pick them up. If an item is very custom (with unique mechanics), the Python service might handle it explicitly (for instance, if “Ghost Ticket” is an item that allows a one-time resurrection, the bot might have to know that logic – this can be scripted in the service as a special case).
- Documenting Custom Enhancements: It’s important to keep track of what we change in the library. We will maintain a CHANGELOG or README detailing:
	- New classes added (e.g., Artificer, Blood Hunter – added from UA content).
	- New subclasses or backgrounds (e.g., School of Geometry (Wizard subclass) from homebrew).
	- Any modifications to rules calculations (if we adjust how an ability works or add a new condition).
We’ll note sources for each addition (for example, “Artificer class data from UA 2019, loaded via JSON; implemented Infuse Item feature manually”). This helps future maintainers or players understand the provenance of the rules. Since Unearthed Arcana is playtest content, clarifying which revision we used (e.g., Artificer V2 vs V1) is helpful.
Currently, scanning the repo reveals some likely custom content: the commit history shows PDF sourcebooks including “UA - Artificer.pdf (v1 and v2)”, “Blood Hunter Class 1.2.pdf”, and others. These indicate the intention to support Artificer and Blood Hunter classes (the latter being a popular homebrew class by Matt Mercer). We will confirm that our library has corresponding data for these classes. If not, we’ll create it from those PDFs. For example, for Blood Hunter we might create a subclass of Fighter or Ranger in code, or just use Character and manually apply the Blood Hunter’s unique features (the “Crimson Rite” etc.) as needed for our game.

Leveraging the Library in Workflows: Once updated, the dnd-character library (via the Python service) will be used in various n8n workflows:
- **Character Creation Workflow**: We plan to support either random character generation or guided creation. The library can generate a random character (it has CLI support for random generation). We will wrap this in an API call. A player using /createcharacter could trigger a workflow that asks the Python service to generate a character (maybe with certain parameters like class or completely random). The result can be returned as a formatted stat block. This ensures any generated character is rules-legal (attributes rolled 4d6 drop lowest, starting equipment assigned, etc. per the library’s logic).
- **Character Selection**: Since we have a preset character list for the one-shot, we might implement a workflow where players pick one of those pregenerated characters. For example, /choosecharacter "Stephanie Efforts" would load the Artificer character profile. We have those presets written in narrative form (with archetype and backstory) in the repo. We’ll need to also have their actual stats prepared. We can either pre-generate their stats using the library and store them (perhaps in JSON or as Character objects pickled), or define them manually if specific. The workflow can then fetch that data and acknowledge the selection. This way, CC will know which character is speaking to him (the Slack persona prompt already suggested the players had created their characters).
- **Stat Queries and Calculations**: If a player asks in character, “Can I make that jump?”, the DM could ask CC to calculate something (maybe an ability check DC). While the LLM can respond in a narrative way, we also have the ability now to calculate probabilities or do actual dice rolls through the service. We could create a command /check athletics [DC] and the bot will roll the character’s Athletics skill vs a DC and narrate the outcome. This blends mechanics with storytelling seamlessly.
- **Homebrew Rules Support**: Our campaign may introduce custom rules (e.g., a “tech fatigue” mechanic or a special artifact effect). These won’t come from the library or books. We can support them through n8n logic or Python code. For instance, if there’s a custom condition that isn’t in 5e SRD, we can detect it in the chat context and have the bot explain it consistently (perhaps by storing a description in the lore JSON). For more mechanical homebrew (like a custom spell), we add it as a data entry so that if the bot is asked, it knows the details.

In short, the updated dnd-character library will serve as the rules engine behind ColmCast v2. It provides all the crunch: classes, items, leveling, combat calculations (to an extent), and serialization of characters to/from dicts. Our job is to extend it to cover the full scope of our game (including UA and custom content) and expose it via the service. Any enhancement we make (data or code) will be documented for transparency. This ensures the bot’s decisions can be traced to actual D&D rules or specified homebrew, which is crucial for player trust. There’s nothing worse than an “AI DM” making up unfair rules – by grounding ColmCast’s game logic in the same rulebooks the human DM uses, we maintain fairness and consistency. Notably, the repository already reflects some custom enhancements:
- The presence of an Artificer profile in the preset characters (Stephanie Efforts is listed as an ARTIFICER in Lawful Neutral) shows that we intend to have that class playable. We’ll ensure the class features (like Infusions, etc.) are available. Perhaps we won’t simulate every feature (some might be handled narratively), but key mechanical ones (spell slots for an Artificer, or their tool proficiency bonuses) should be there.
- Inclusion of Banksy (ROGUE), Camila (WIZARD), etc., are standard classes, but the Blood Hunter PDF suggests maybe an NPC or additional option. We’ll clarify if any player is using Blood Hunter or if it’s for an NPC – either way, adding it to the library means the bot can answer if asked “What is a Blood Hunter?” or roll one if needed.

By integrating these enhancements, ColmCast v2 can confidently support both standard D&D 5e and our campaign’s unique content. The dynamic between the LLM and the rules engine will be that the LLM focuses on storytelling and creative language, while the rules engine provides factual backbone (e.g., “you have +7 to History skill” or “the spell Lightning Lure pulls the target 10 feet”). This combination will make CC feel like a knowledgeable, reliable yet unpredictable NPC – just what we need for a memorable game session.

For example, an item “EffortNet Drone” for Stephanie Efforts, or Cassidy’s custom Artifact “PATH Control Rod”. These items have entries in the equipment JSON with relevant stats (weight, properties, maybe a description). Additionally, mundane items from sourcebooks (like firearms from the DMG or Eberron) are added since the campaign has a modern arcane tech vibe. The modern and futuristic gear from sources like Dungeon Master’s Guide (modern weapons) and Eberron are thus accessible.
- **Spells**: All spells from sourcebooks beyond the SRD are included (e.g., Mind Sliver, Summon Draconic Spirit from Tasha’s, etc.). The SPELLS dictionary in the library now covers these since the data from 5e-database is comprehensive. If any custom spells were invented for the campaign, they are added to the cache as well. For instance, if there’s a spell “Archive Pulse” that ColmCast uses, we define its level, school, casting time, etc., in a format similar to other spells so it can be treated like one.
- **Rules Variants**: If we are using any variant rules (like gritty realism rest or hero points), those aren’t directly in the library but we document them and adjust workflows accordingly. For example, if short rest is 8 hours in our game, the bot’s advice or mechanics (like hit dice recovery) will reflect that in responses.

We will maintain a “ColmCast dnd-character Addendum” document (likely in the repo’s artefacts or wiki) listing each enhancement. Each entry will have:

- What: e.g., “Added Artificer class (Unearthed Arcana 2019)”.
- How: e.g., “Data – classes_artificer.json, classes_artificer_levels.json; Code – new class Artificer in classes.py subclassing HalfCaster mixin; Items – added Infusions as special items in items.json for tracking.”.
- Impact: e.g., “Players can create Artificer characters. Spell slots calculated as for a half-caster. Infusions not fully automated (DM will handle their effects manually).”
- Source/License: e.g., “Content from UA is © Wizards of the Coast (fair use in private game). Blood Hunter by M. Mercer, used with credit.”

By thoroughly documenting these, we ensure that any future updates to the library (or migration to a different system) won’t accidentally lose these homebrew extensions. It also helps in debugging – if a weird value shows up in a character sheet, we can trace if it came from a custom rule we inserted. In conclusion, the custom enhancements to dnd-character primarily involve broadening the content scope (to include all the rich options we want to give players or our NPCs) and tweaking a few mechanics to fit our game’s needs. These have been identified and recorded so that ColmCast v2’s game logic is transparent and verifiable. The result is a tailored rules engine that underpins the storytelling with real D&D mechanics, even for homebrew elements.

### Containerization, Deployment, and Maintainability
With the design laid out, deploying ColmCast v2 will involve setting up a containerized environment and establishing good DevOps practices for maintainability:

- Docker Compose Deployment: We will use a Docker Compose configuration to define our multi-container setup. An example docker-compose.yml will have services like:
	- n8n – using the official n8n image (with maybe minor customizations for any additional nodes we install, like the Discord nodes). We’ll mount a volume for n8n to store its database (SQLite file or Postgres data directory) so that workflows and credentials persist across restarts. Environment variables will supply N8N credentials, the base URL (if we expose it via web), and any necessary config (for instance, turning off telemetry, etc.).
	- colmcast_api – a custom image we build from our Python service code. This image will be based on a Python 3.x slim base, copy in our dnd-character library (with enhancements) and our Flask/FastAPI app code. It will expose a port (say 8000) for the REST API. We’ll likely mount the storage directory with the FAISS index as a volume, so that the index can be updated or persisted without rebaking the image each time (alternatively, we bake a static index into the image if it’s not huge). The container will also include the PDF texts if needed or any data files. However, since we’ve likely processed those PDFs into the index already, the service might not need the actual PDFs at runtime.
	- postgres (optional) – if we choose Postgres for n8n’s backend or for storing game state (characters, etc.), we include it here. Otherwise, n8n can use a built-in SQLite and the game service can use in-memory or its own files for state.

We will configure the Compose file such that the n8n service can talk to colmcast_api by name (Docker DNS). In n8n workflows, the HTTP node will call http://colmcast_api:8000/endpoint. This decoupling means we don’t expose the Python API to the public internet – it’s only accessible within the Docker network (for security, since it might not have auth on it).

#### Building the Images: 
We’ll create a Dockerfile for the colmcast_api. It will:
- Pull a base image (Python 3.11 slim, for example).
- Install system packages needed (maybe ffmpeg or other library if needed for PDF parsing, but likely just pip packages).
- Copy in our requirements.txt or use Poetry if we have one. This will include dnd-character (we might just list it as a local path or wheel if we forked it), Flask/FastAPI, and other dependencies like numpy, faiss-cpu, etc. (We saw these in environment.yml: we will streamline that for just what the service needs – slack-bolt, for example, will be omitted).
- Copy our application code (the Flask app, etc.) and expose the port.
- Set an entrypoint to run the app (e.g. gunicorn main:app if using FastAPI with Uvicorn workers, or just python app.py for Flask development).
We’ll version these images appropriately (maybe tag as colmcast-api:v2). For n8n, we may not need a custom image unless adding custom nodes; however, if using community nodes, n8n now supports installing those at runtime via the UI or via mounting files. We can simplify by manually installing the Discord trigger node through the UI once, and it persists. Alternatively, build a custom n8n image that pre-includes that node package (this might be overkill).

#### Environment & Secrets: 
All secrets (OpenAI API keys, Discord bot token, etc.) will be supplied via environment variables in the compose file (or, better, a .env file referenced by compose). For example, DISCORD_TOKEN, OPENAI_API_KEY. N8n can reference these in its credentials configuration. The Python service will need OPENAI_API_KEY as well if it does embeddings or GPT calls internally (though ideally it won’t after we shift that to n8n, except perhaps for embedding new texts). We will not hard-code any credentials in code or images, for security and ease of rotation.

#### Reverse Proxy (if needed): 
If we want to expose n8n’s web interface for editing or need to accept incoming webhooks from Discord, we might include a simple reverse proxy container (like Caddy or Nginx). The forked n8n-hosting repo actually provides a Caddy example. We could use Caddy to handle HTTPS and route /webhook/* to n8n, and maybe password-protect the n8n editor. Since this is likely a private game, we might not need a domain name or heavy HTTPS – but for security (especially if running on a cloud VM), we should at least enable HTTPS for the n8n endpoint (because it will carry the Discord interaction tokens and possibly other sensitive info). Caddy or Nginx with Let’s Encrypt can automate this.

#### Deployment Target: 
We will deploy on a suitable host – possibilities include a small cloud server (AWS Lightsail, DigitalOcean droplet, etc.), or a platform like Heroku/Dokku for the services. n8n can also run on services like Docker Compose on Azure. Given the need for persistent connections (for Discord interactions we might rely mostly on webhooks, so it’s fine), a single VM with Docker Compose is straightforward. The compose stack will be set to restart always, so if the VM reboots or a container crashes, it comes back up. We’ll also ensure to backup the n8n workflow data (which could be simply the volume or DB dumps).
#### Logging and Monitoring: 
Each container will log to stdout/stderr, which Docker captures. We can use docker-compose logs -f during debugging. For more robust monitoring, we might set up alerts or use a minimal solution like healthchecks or uptime monitor ping. For instance, n8n has a heartbeat URL we can ping or we can have a dummy workflow that pings a watchdog service to confirm it’s alive. The Python API can have a /health endpoint that returns OK, and we could use Docker HEALTHCHECK to monitor it. This way, if the API ever gets stuck, Docker could auto-restart it.
#### Maintainability of Workflows: 
One challenge with n8n is managing workflows as code. We will keep an export of the workflows (n8n allows exporting flows as JSON) in the Git repository for version control. After designing the flows in the n8n UI, we’ll export them to a JSON file (or use n8n’s CLI if available) and store it (maybe in an n8n_flows/ directory). This ensures that if we need to rebuild n8n or track changes, we have them. It also serves as documentation of the logic. We can even create a script to import these JSONs into n8n on startup, but since we plan to persist n8n’s own database, that might not be necessary except for disaster recovery.

#### Updating Components:
Updating the Python service is as simple as building a new Docker image (we can tag by version). We should write unit tests for critical functions (e.g., character generation, any custom rule functions) to avoid regressions. Upon changes (like adding a new class), run tests, then deploy the new container. Docker Compose can do rolling restart with little downtime for the bot (since n8n can queue incoming messages briefly).
Updating n8n workflows does not require container changes – those can be done live through the editor. However, we might occasionally update the n8n image to get new features or bug fixes. We’ll pin a version initially (to ensure stability during the session) and plan upgrades in between campaigns.
#### Security: 
We will restrict external access appropriately:
The n8n instance’s editor UI should be behind an authentication. N8n supports basic auth or its own user management. We’ll enable that so random internet users can’t meddle with our workflows.
The Discord webhook endpoint (if used) can be long and unguessable, plus Discord signs its requests – we will verify those signatures in n8n (the community node likely does this). This prevents outsiders from triggering our workflows.
Our OpenAI key stays on the server side; the players and Discord never see it. Same for any other keys.
#### Testing and Staging: 
Before the live game, we likely set up a test Discord server and run the bot there to ensure everything works (commands, responses, multi-step interactions). Because containerization makes it easy to spin up the whole stack on a local machine or separate environment, we can test with dummy data without affecting the real game server. This staging area can use a separate Discord bot token if we want to keep it totally isolated.
#### Performance Considerations: 
GPT-4 API calls are the slowest part (2-5 seconds each). The rest (DB, Python calculations) are fast. N8n introduces a small overhead to orchestration, but it’s negligible compared to network calls. One performance tweak: the FAISS index query is local and under a second typically; we just need to ensure the embedding model (if needed) is loaded once. The Python service will handle that by loading the index at startup, so queries are in-memory thereafter. We should give the container enough memory (FAISS with all those sourcebooks might use a few hundred MB, which is fine).
#### Backup: 
We will regularly back up:
- The n8n database (workflows, creds).
- Any important game state (if characters are stored in a database or as JSON, back those up).
- The FAISS index files (though these can be re-built from source PDFs if needed, having a backup is faster).
- Possibly transcripts of sessions (the Slack version logged conversations; we might log Discord chats similarly, perhaps via n8n writing to a file or Google Doc). These logs are useful for the DM and also serve as a backup of what transpired in case of disputes or recap needs.
By following these deployment practices, maintaining ColmCast v2 will be relatively straightforward. The modular containers mean that, for example, if a new version of the dnd-character library or a new OpenAI model comes out, we can upgrade the Python service or the n8n workflows independently. If Discord changes an API, we update the integration node without overhauling the entire system. Furthermore, containerization sets us up for potential reuse and scalability: If in the future ColmCast is to be used for another adventure or offered to others, one could package this whole setup and deploy it elsewhere with minimal fuss (just provide new config values and run the compose). It also means if one component fails (say the Python service crashes), the rest (n8n and Discord connection) can keep running – n8n could even catch the error and notify the admin, then wait for the service to restart. In essence, we are trading the simplicity of “run a script on my laptop” for a robust, production-style setup that ensures ColmCast v2 is always available and easy to evolve. This investment in DevOps will pay off in the reduced effort to fix bugs or add features during the heat of the campaign.

## Implementation Plan: From Slack Bot to Discord Automation
Based on the above evaluation, here is a phased implementation plan to realize ColmCast Chatbot v2:
### Phase 1: Environment Setup & Basics
- Set up Repositories: Create a new repository (or branch) for ColmCast v2 infrastructure. Organize the code into n8n_workflows/, colmcast_service/ (Python code), etc. Include a README outlining how to build and run.
- Dockerize n8n: Using the n8n-hosting example, write a docker-compose.yml with an n8n service. Configure it to use a local volume for /home/node/.n8n (to persist data). Initially, bring up n8n and ensure you can access the UI (likely at http://localhost:5678). Set an admin user/password.
- Discord Bot Registration: Create a Discord Bot through the Developer Portal. Give it a name (e.g., “ColmCastBot”). Generate a Bot Token and save it. Enable Privileged Gateway Intents if needed (we might not need presence/member intents for this use case). Add a slash command (in the Developer Portal or via code) for a simple test, like /ping (for initial connectivity testing). Invite the bot to a test server.
- Connect Discord to n8n: Install the community Discord Trigger & Send nodes in n8n (if not using webhooks). Configure the Discord credentials in n8n using the Bot Token. Create a simple workflow in n8n: Discord Trigger (for /ping) → Respond with Discord node (“Pong!”). Test this on the Discord server by typing /ping. Adjust any permission issues until the bot responds successfully.
- Basic Conversation Workflow: Implement a basic version of the DM chat workflow. For now, it can ignore RAG and the Python service:
- Trigger: (Temporary solution) Use a Discord slash command like /ask with a text parameter, to simulate a DM message. (Later we will handle actual DMs).
- Action: Use an OpenAI node (or HTTP request) to send a prompt to GPT-4. For testing, a simple system prompt “You are CC, a witty AI.” and user prompt from the slash command text is fine.
- Response: Take GPT output, and use Discord Send node to reply (ephemeral or channel message).
- Verify that the round-trip works: the model responds and the message appears on Discord.
### Phase 2: Python Game Logic Service
- Service Scaffold: In colmcast_service/, set up a basic Flask or FastAPI app. Implement one test endpoint, e.g., GET /hello that returns “world” to verify connectivity. Write a Dockerfile and build the image (docker build -t colmcast-api .). Update docker-compose.yml to include this service, and link it with n8n’s network.
- Integrate dnd-character: Copy or install the dnd-character library into the service. Ensure the container has all needed dependencies (faiss, numpy, etc.). In the app, add an endpoint /create_character that internally uses dnd_character.Character or class constructors to create a new character. For start, it can create a random Level 1 character with default parameters. Test this by calling the endpoint (e.g., via curl inside the container or an n8n HTTP node) – it should return some character data (JSON or text).
- Load FAISS Index: Move the existing FAISS index files (from storage/faiss_index in the Slack bot) into the service container (consider adding them via Dockerfile or mounting a volume). In the app startup, load the index using LlamaIndex as done in rag_retriever.py. Implement a POST /query_rules that accepts a question and returns the retrieved context (the concatenated top 3 passages, for example). Test this endpoint with a sample question (“What is a concentration spell?”) and see that it returns a relevant snippet (e.g. from the Player’s Handbook rules on concentration).
- Extend Character Generation: Expand /create_character to accept parameters – class, level, maybe race/background. Utilize the library to generate appropriately. For example, if class is specified, instantiate that class from dnd_character.classes. If level is given, set it and call .level_up() if needed to reach that level. Include equipment. This will use SRD data for now – we’ll incorporate custom data later.
- Persistent Storage (if needed): Decide how to store created characters or selected pregens. A simple approach: the service can keep them in memory (in a dict mapping user ID to Character object). But to persist across restarts, use either a tiny SQLite (since we already have SQLAlchemy via library if needed) or allow n8n to request the full data and store it on its side (not ideal). Perhaps implement endpoints: /characters (GET all or POST new) and /characters/{id} for fetch/update. We can generate a character ID when creating. For the one-shot, an in-memory might suffice, but persistence is safer.

### Phase 3: Feature Parity Implementation
- Player Profile Integration: Import or recreate the player_profiles.json from Slack bot into our new system. We can either embed that data into the prompt for GPT (like v1 did) or have the Python service manage some of it. Given the persona prompt already covers a lot, we might store profiles in n8n (in a static data structure or in the Python service as a dict) and retrieve relevant info to append to system prompt or as context. Implement a lookup such that when user X messages, the workflow fetches X’s profile (e.g., “Jordan Lumberpond, Bard, NG, famous musician…” from the JSON) and inserts a line about it into the prompt. This ensures CC’s responses remain tailored.
- Lore Data: Similarly, port lore.json (if it contains specific world lore or hints). Make it accessible to the bot – maybe also via the vector index if it’s textual, or as a short context that’s always included. Ensure CC doesn’t reveal secrets unless appropriate (the persona instructions already cover that).
- In-Character Chat Workflow: Now assemble the full Chat workflow in n8n:
	- Trigger: Use a Discord Message Create trigger for DMs to the bot (if using the community trigger, or if not available, fall back to using a slash command like /cc in a server channel that denotes an IC question).
	- Actions:
		- Identify the user and their character (if we have a mapping from Discord user to character).
		- Formulate the system prompt. This will combine: the core persona (from Slack but updated if needed), the player’s profile snippet, possibly a summary of recent conversation (we can retrieve last few messages from an in-memory store or Discord history API), and a placeholder for rule context.
		- If the message seems to be a rules question or contains a D&D term, call the /query_rules on our service to get relevant info. We could use a simple heuristic or always query it and let the LLM decide to use it. In v1, they always pulled some context (similarity_top_k=3). We can do the same: send the user’s message to /query_rules, get up to 3 passages, and include them in the prompt as “D&D Rulebook Excerpts:\n”.
		- Send the composed prompt (system + excerpts + conversation history + user query) to OpenAI (GPT-4) via the OpenAI node.
		- Take the response, log it (maybe to a file or simply to the n8n execution log), then send it back to the user on Discord.
- Testing: Try a sample DM: “Hey CC, can my artificer use a longsword effectively?” Expect the bot to respond with some in-character snark plus the mechanical answer (e.g., explaining artificers are proficient with martial weapons if they have that background, etc., drawn from context).
- Dice Roll Workflow: Implement the /roll slash command workflow:
	- Trigger: Discord slash command /roll with a string parameter (like “1d20+5”).
	- Action: Use either a small JS function node or call a Python endpoint to parse and roll. For simplicity, we might incorporate a tiny dice library in Python service (there are many on PyPI, or we write a quick parser using regex).
		- The Python service returns the result (e.g., “Rolled 1d20+5: 13 + 5 = 18”). The n8n workflow then replies with that string in Discord.
		- Test with various inputs, including edge cases (“3d6”, “d%, etc.). This ensures players have a handy roller. (Even if they roll their own physical dice, it’s nice for CC to do some rolls for secret checks or NPCs.)
- Character Management Commands: Implement selection of pregenerated characters:
Perhaps a command /list_characters that lists the available pregens (names and brief intro). This can output an embed with each character’s emoji and summary.
/choose_character name: The workflow finds the chosen pregen (we can store preset characters in a JSON or the Python service could have them predefined in a module). It then records this choice (e.g., in a database or in n8n’s memory) tying the Discord user to that character. It confirms to the user (“You have chosen to play Stephanie Efforts, the Artificer.”).
We’ll have to have the stats ready: we might pre-create these characters using the library and store their JSON stat blocks. If time permits, create a script to generate them at level 10 with appropriate gear and manually adjust anything to fit their concept (like custom magic items or specific ability scores to match their archetype). Load these into the Python service (perhaps as part of its startup, from a file).
Once a user has chosen a character, the chat workflow can automatically pull their character’s info for context. For example, we might add to the system prompt: “(Player’s character: Level 10 Artificer with 18 INT, carrying an Arcane Focus Drone)” or even have CC know that info to incorporate in replies (“Ah, a clever Artificer like you, with all your gadgets…”).
Game-Specific Mechanics: Implement any known special commands needed for our scenario:
If there’s a puzzle where players might ask CC for hints, perhaps a command /hint triggers a workflow that either uses some logic or randomly picks a clue from a list.
If CC is meant to “resist” giving direct answers (as a character), we might implement a threshold – e.g., require a Persuasion roll. In that case, a workflow could intercept certain questions and require a dice roll outcome before proceeding to call GPT (this could be a fun integration: the bot might say “CC eyes you warily, uncertain if he should reveal more…”, then prompt the player to roll persuasion).
Ensure safety nets: we should decide how to handle if GPT produces something inappropriate or lore-breaking. Possibly keep the moderation strategy from v1 (not directly mentioned, but presumably relying on GPT-4’s moderation or our careful prompt). If something goes awry, since we’re there as DM, we can always step in – but as a backup, we could add a check: the workflow can scan GPT’s output for forbidden content or major spoilers (we can maintain a list of true campaign secrets that should not be revealed, and if the answer contains them, either redact or re-roll with a stricter prompt).
Phase 4: Testing and Iteration
Alpha Test: Gather a small group of testers (could be just the DM and one player or friend) to run through a mini-conversation on Discord. Test every command:
DM chat in character, ask both simple and complex questions (lore, rules).
Roll some dice.

Monitor the logs for any errors or slow points. This will also train players on using the commands. Gather feedback: Are the commands intuitive? Is CC responding too slowly or quickly? Are there requests for additional features (e.g., “Can CC show us an image?” – maybe we integrate an image generation for fun via a future stable diffusion if desired; or “Can CC track our HP?” – maybe a feature to log HP changes).
Tweak & Tune: Based on testing feedback:
Adjust temperature or response length from GPT if needed (maybe CC should be more concise or more poetic).
Fix any bugs (e.g., a crash in Python service if an unknown class is requested – add graceful handling).
Expand homebrew support if testers tried something and got an “I don’t know that” – for example, if a tester asked about a subclass we forgot to add, go ahead and add it.
Update documentation with any new decisions (if we decided to cut a feature or add something last-minute, record it).
Go-Live Preparation: Before the real session:
Performance Check: Rebuild the FAISS index if new content was added (run build_index.py on all the final PDFs and ensure the index file is updated). The sourcebooks loaded include a huge trove, which is great – but confirm the index size is manageable and that memory usage is within container limits. Possibly allocate more RAM to the container if needed.
Backup: Take a snapshot of the entire setup (export workflows JSON, backup volumes, etc.).
Logging: If wanting to record the session, have a plan – maybe a workflow that appends all CC’s messages to a log file or Google Doc. This can be done by adding a side-action in the main chat workflow (n8n can do multiple actions in parallel: one to respond, one to log). Alternatively, Discord’s chat log can serve as record (just ensure nothing gets lost).
Deploy on Production environment: If tests were on a local machine, now deploy the stack to the cloud server intended for the game. Set up domain if needed for webhooks, ensure all environment variables are correctly set on the server.
Run a final smoke test on the production environment’s Discord server to ensure everything survived the move (usually it should if environment is same, but checking API keys, etc.).
Session Running: During the actual game sessions, monitor the system:
Keep an eye on resource usage (with GPT-4 calls and vector searches, CPU should be fine, memory mostly for index ~ a few hundred MB, network usage minimal except OpenAI).
If any issue arises mid-session (bot not responding, etc.), have a fallback – e.g., be ready to restart a container. Docker-compose makes this quick; n8n will resume and catch up on any missed webhooks (or the slash command can be reissued).
Use the maintainability features we set: if the DM wants to tweak CC’s behavior live (say CC should become more cryptic), we can edit the system prompt in n8n on the fly and save – the next responses will use the new prompt immediately. This dynamic control is a big win for v2.
Post-Session Review: After each game, review the interaction logs:
Were there questions CC couldn’t handle? (Add those answers or context next time.)
Did any rules answers seem incorrect? (Might indicate missing or wrong data in our knowledge base – update that content or adjust the retrieval query.)
Are players engaging well with the bot, or are they unsure of how to use it? (This may suggest adding more guidance or simplifying certain interactions.)
Iterate on the workflows or service as needed for subsequent sessions.
